# 浮窗昨收口径修改方案

> 状态：**已实施**（2026-10-13 设计 → 实施 → 验证，见 §8 实测结果）
> 目标：消掉除权日「图上一个数、浮窗另一个数」的自相矛盾。
> 手段：**不改图、不改任何算法**，只让浮窗显示库里本来就有的字段。
>
> 本文分两部分：
> [一、日K](#一日k-的处理办法) —— 下发 `pre_close`，浮窗昨收取它；
> [二、周期K](#二周期k-的处理办法) —— 删除冗余列，补上除权标注。

---

## 一、日K 的处理办法

### 1. 要解决的现象

除权日，浮窗里这几个数字互相打架。

以恒生电子（`SH.600570`）2026-06-09 为例（当日每 10 股派 2 元）：

| 字段 | 现在显示的值 | 来源 |
|---|---|---|
| 昨收 | 22.26 | 前一根 `close` |
| 今开 | 22.26 | 库里 `open` |
| 今价 | 22.27 | 库里 `close` |
| 涨跌 | +0.21 / **+0.04%** | 库里 `chg_pct`（Tushare 官方值 +0.95%） |

**问题**：`昨收 22.26` 和 `今价 22.27` 摆在一起，只涨了 0.01 元；
但浮窗底下写的涨跌幅是 **+0.95%**。用户盯着同一块屏幕，三个数对不上。

根子在这一天 6/8 的收盘价是 22.26，而交易所给的除权参考价是 22.06
（22.26 − 每股派息 0.20）。**官方涨跌幅用的正是 22.06，不是 22.26。**

### 2. 根因

库里 `kline_day` 的这一行同时存了两个数：

```
2026-06-09
    close      = 22.27     ← 图上画这个
    pre_close  = 22.06     ← 官方涨跌幅拿这个当基准
    chg_pct    = 0.95      ≡ (22.27 − 22.06) ÷ 22.06
```

- **图**画的是 `close` 列（真实成交价序列）
- **涨跌幅**用的是 `close` 与 `pre_close` 两列

**平时这两者天然一致** —— 平时 `pre_close` 就等于前一根 `close`：

| 日期 | 前一根 close | 本根 pre_close | 相等？ |
|---|---|---|---|
| 06-04 | 24.29 | 24.29 | ✅ |
| 06-05 | 23.56 | 23.56 | ✅ |
| 06-08 | 23.15 | 23.15 | ✅ |
| **06-09** | **22.26** | **22.06** | ❌ |
| 06-10 | 22.27 | 22.27 | ✅ |

5435 根日线里**只有 23 个除权日会分叉**，其余 5412 天完全一样 ——
所以这个问题一直很隐蔽。

**但显示层自己制造了第三个口径。** 浮窗的「昨收」栏不取库里的 `pre_close`，
而是取**前一根 `close`**，于是又多出一个「22.26」，和图上的口径绑在一起、
和库里的涨跌幅脱节。

> `pre_close` 目前**根本没下发给前端**（`market._to_bars` 的输出里没有这个字段），
> 它只在后端算复权因子时用。正确的值就在库里躺着，只是没送出来。

### 3. 方案

**浮窗的「昨收」栏改用库里的 `pre_close`**，除权日不再显示「前一根 close」。

| | 昨收 | 今价 | 涨跌 | 读起来 |
|---|---|---|---|---|
| **现状**（前一根 close） | 22.26 | 22.27 | +0.04% | 三个数打架 |
| **改成**（`pre_close`） | **22.06** | 22.27 | **+0.95%** | 内部自洽 |

**这正是行情软件的标准做法**：浮窗的「昨收」显示交易所给的除权参考价，
不是前一根的原始收盘。所以在 2021-07-16（10 送 4）那天，通达信显示的是
「昨收 61.72」而不是 86.50 —— 用户不会误以为那天暴跌了 27%。

#### 改动清单

| # | 位置 | 改什么 | 备注 |
|---|---|---|---|
| 1 | `market._to_bars` | 输出增加 `pre_close` 字段 | 现在根本没下发 |
| 2 | `market._apply_adj` | 复权档下 `pre_close` 与四价一样乘因子 | **必须加**，见下 |
| 3 | `CrosshairTooltip` | 昨收栏优先取 `pre_close`，取不到再回落前一根 `close` | 保留回落，首根无昨收时要用 |

**第 2 条为什么必须**：一旦 `pre_close` 出接口，复权档下它就得跟着价格一起缩放
（`_apply_adj` 现在已经缩放 `open/high/low/close` 和 `chg_amt`）。忘了这行，
`adj=qfq` 下会**再分叉一次** —— 只是分叉的那天和现在不是同一批。

### 4. 为什么不用动别的

| 方案 | 评价 |
|---|---|
| **改浮窗昨收栏**（本方案） | 库里数据正确、图上价格正确，只有显示少取了一个字段。改动最小 |
| 改 `kline_day.chg_pct` | ❌ 那是 Tushare 官方 `pct_chg`，全行业都这么显示。改了就和所有行情软件对不上 |
| 改图（用复权价画） | ❌ `adj=none` 的语义就是「看原始价」，改成复权等于这个档位名不副实 |
| 库里再存一列原始口径 chg | ❌ 纯冗余，完全能从 `close` 推导；还要多一列同步 |

### 5. 影响面

| 范围 | 影响 |
|---|---|
| 日线的 23 个除权日 | **唯一会变的** —— 昨收栏数字不同，涨跌幅不变 |
| 日线其余 5412 根 | 零影响（`pre_close` 本来就等于前一根 `close`） |
| 派生周期（周/月/季/年） | 零影响 —— `kline_period.pre_close` 本来就等于前一根 `close`；该列已在第二部分删掉 |
| 接口 | 每根 bar 多一个 `pre_close` 字段，可空 |
| 配色逻辑 | 不涉及。当前配色也比的是前一根 `close`，改成 `pre_close` 后反而更准 |

> ⚠️ 派生周期那一行原写作「零副作用，所以可以走同一条下发通道」。
> **第二部分推翻了它**：`kline_period.pre_close` 是冗余列，直接删掉，
> 周期K 的昨收走 `prevClose` 回落即可，见 [二、周期K](#二周期k-的处理办法)。

### 6. 仍未解决的

**图上的跳空本身还在。** 图画的是原始价序列，那个基准下调没有被抹掉，
2021-07-16 那种大送转仍然是根暴跌大阴线。

但本方案把矛盾的性质改了：「图 vs 数字」变成「图 + 一个解释」——
用户看到「昨收 22.06 ≠ 图上前一根 22.26」自己就明白这天除权了。
再配合已有的 `$` 除权标记（点开弹窗是「每10股派2元」），信息链是完整的。

**要让图本身也连续，只有切复权档**，那是另一个话题。

### 7. 待确认

> **一处措辞歧义**：讨论时说的是「把 `pre_close` 显示成 **open** 价格」。
>
> 若字面执行会出错 —— 2026-06-09 的实际开盘价是 22.26，
> `pre_close` 22.06 是**昨收**，不是开盘价。开盘价是当天真实报出来的数，不该替换。
>
> 本方案按「**昨收栏**用 `pre_close`」理解。要改成别的口径请先确认这一点。

### 8. 验证判据

改完后按这几条验，**判据要独立于被验证对象**（实测结果见 [二、周期K](#二周期k-的处理办法) §8）：

| # | 判据 | 通过标准 |
|---|---|---|
| 1 | 浮窗昨收 == 库里 `pre_close` | 除权日与平常日**全部**相等，不一致 0 根 |
| 2 | `昨收 + chg_amt == 今价` | 23 个除权日逐根成立（现在这 23 根是不成立的） |
| 3 | 派生周期无变化 | 改前改后 `kline_period` 相关输出**逐根完全相同** |
| 4 | 复权档未退化 | `adj=qfq/hfq` 的 `pre_close` 与四价同倍缩放，相邻两根源子比 == `1 + chg_pct`，偏差 ≤ 0.01 个百分点 |
| 5 | 接口契约 | `KLineBar` 类型加可选字段，`tsc --noEmit` 通过；旧前端拿到缺字段时走回落分支不崩 |

**第 2 条是这次改动唯一真正要证明的东西**，也是当前唯一不成立的恒等式。
第 3 条是回归保护 —— 派生周期本来就该什么都不变。

## 二、周期K 的处理办法

> **一句话**：`chg` 一个字不改。只做两件事 ——
> 删掉冗余的 `pre_close` 列、补上浮窗的除权标注。

### 1. 现状：两个缺口

| 缺口 | 表现 |
|---|---|
| `kline_period.pre_close` 是**冗余列** | 它就等于上一根 bar 的 `close`，完全能从表内推导，却每次写入都要维护 |
| 浮窗**没有除权提示** | 周期 bar 的昨收恒等于上一根 close，数字本身永远不会提醒用户这个月除过权 |

第二个缺口更要命：日K 除权日「昨收 22.06 ≠ 图上前一根 22.26」，
用户看到数字对不上自然会警觉；而周期K 的昨收和上一根 close **完全相同**，
用户只会把跳空当成暴跌（2008-05 月线 −34.17%，实际 5-28 送转）。

### 2. 删掉 `kline_period.pre_close`（14 列 → 13 列）

**删掉不影响涨跌计算**：`LAG(close)` 只在物化 SQL 的派生表里活着，算完就丢。

```sql
SELECT code, period, trade_date, open, high, low, close,
       volume, amount, ah_vol, ah_amt,
       chg_amt, chg_pct                        -- 不再有 pre_close
FROM (
    SELECT b.*,
           LAG(close) OVER (ORDER BY trade_date) AS prev_raw,   -- 中间量，不落库
           ROUND(close - prev_raw, 2)             AS chg_amt,
           ROUND((close / prev_raw - 1) * 100, 2) AS chg_pct
    FROM ( 桶聚合 ) b
) x
ON DUPLICATE KEY UPDATE ...
```

⚠️ `prev_raw` 必须留在派生表里：MySQL 不允许在同一 SELECT 列表里引用另一项的别名，
而两个 `ROUND` 正是引用 `prev_raw`。

#### 改动清单

| # | 位置 | 改什么 |
|---|---|---|
| 1 | `db._KLINE_PERIOD_DDL` + `MIGRATIONS` | 删掉 `pre_close` 列（14 → 13），库上手工 `DROP COLUMN` |
| 2 | `kline_repo._materialize_sql` | `LAG(close)` 改名为派生表中间量，只输出 `chg_amt` / `chg_pct` |
| 3 | `kline_repo` 的 `_COLS` / `_COLS_PERIOD` / `_UPDATE` | 去掉 `pre_close` |
| 4 | `market._AGGREGATE_BARS`（回退路径） | 同上，与物化保持一致 |

**#1 是破坏性变更**：列已落库 1542 行，`DROP COLUMN` 后该列数据不可恢复
（但它本来就是能推导出来的，丢了没有任何信息损失）。

### 3. 聚合规则与涨跌口径（都不变）

```
open  = 桶内首个交易日的 open     ← FIRST_VALUE，不能用 MIN(open)
close = 桶内末个交易日的 close    ← LAST_VALUE
high  = MAX(high)
low   = MIN(low)
量额  = SUM

chg_pct = 本桶 close ÷ 上桶 close − 1
```

窗口必须显式写 `ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING`，
否则 `LAST_VALUE` 默认只到当前行。

**涨跌图上是什么，数字就是什么**：`adj=none` 用原始价，复权档用复权价。

> **为什么不折算成「真实损益」**：2021-07 月线折算后是 −16.28%（市值口径），
> 但图上是 93.25 → 55.71 的暴跌，用户会以为算错了。
> 要看连续涨幅切复权档，那条路现算、不读表，四个周期实测偏差 ≤ 0.3%。

### 4. 复权档必须「逐根乘因子再分桶」

| | `adj=none` | `adj=qfq/hfq` |
|---|---|---|
| 做法 | 直接读物化表 | 从 `kline_day` **逐根乘因子再分桶** |
| 为什么 | 通达信就是这样 | 先聚合再整体乘会取到「除权前的最高」和「除权后的最低」，两个数不在同一基准 |

**含除权的桶里，`high` 和 `low` 很可能分别取自除权前和除权后**：

```
2021-07 月线（桶内 22 个交易日，07-16 送转 10 送 4）
  原始    MAX(high)=93.82  MIN(low)=51.17  →  振幅 83.3%
  折算后  MAX(high)=50.24  MIN(low)=38.40  →  振幅 30.8%
```

那 52.5 个百分点的「振幅」是除权断层造出来的，不是真实波动。
`adj=none` 下**保留原样**（用户要看的正是当时的真实报价范围），
`adj=qfq/hfq` 下必须逐根折算 —— 这一条已实现。

### 5. 前端：一条路径，两种取值

```typescript
const 昨收 = extra?.preClose ?? prevClose;
```

| | 取值来源 | 显示效果 |
|---|---|---|
| 日K | 库里下发的 `pre_close`（除权口径） | 除权日显示 22.06 ✅ |
| 周期K | 回落 `prevClose`（数组前一根） | **与现在完全相同**（本来就是同一个数） |

前端不需要「当前是哪种周期」的分支 —— **一个 `??` 覆盖两种情况**。

#### 改动清单

| # | 位置 | 改什么 |
|---|---|---|
| 5 | `market._to_bars` | 输出增加 `pre_close`（**日K 用**；周期K 自然为 None） |
| 6 | `market._apply_adj` | 复权档下 `pre_close` 与四价同倍缩放（**必做**，否则 qfq 下又分叉） |
| 7 | `MarketChart` 的 `tooltipData` | 带上 `preClose` 与 `xdxrDate` |
| 8 | `CrosshairTooltip` | 昨收取 `preClose ?? prevClose`；含除权时显示 `xdxrDate` 一行 |

### 6. 补上浮窗的除权标注

周期 bar 的昨收和上一根 close 相同，**数字永远不会提示除权**，必须显式标注。

数据现成：`is_xdxr` + `xdxr_date` 实测 month / quarter / year **23/23** 全覆盖、
week 20/23（受 `MAX_COUNT=1000` 截断，前端翻页可补），
只是没往浮窗里传。补上后：悬停 → 看到「除权 2008-05-28」→ 点开弹窗看到「10 送 4」。

### 7. 验证结果与东方财富对照

#### 7.1 自洽性体检（2026-10-13 实测）

**判据独立于聚合实现** —— 只检查接口返回的 OHLC 四个数之间的关系：
`open` / `close` 必须落在 `[low, high]` 内，且 `high ≥ low`。

| 周期 | adj=none | adj=qfq | adj=hfq | 含除权的 bar |
|---|---|---|---|---|
| week | 0 异常 | 0 异常 | 0 异常 | 20 |
| month | 0 异常 | 0 异常 | 0 异常 | 23 |
| quarter | 0 异常 | 0 异常 | 0 异常 | 23 |
| year | 0 异常 | 0 异常 | 0 异常 | 23 |

**合计 89 个含除权的 bar，三个复权档各验一遍，0 异常。**

#### 7.2 与东方财富对照

用户提供了东财「周线·前复权」的截图，同一周（2026-06-08~06-12）对照：

| | 开盘 | 最高 | 最低 | 收盘 | 涨跌幅 |
|---|---|---|---|---|---|
| 我们 `adj=none` | 22.68 | 23.15 | 20.91 | 21.71 | −6.22% |
| 我们 `adj=qfq` | 22.48 | 22.94 | 20.91 | 21.71 | −5.36% |
| 东财 前复权 | **35.80** | — | — | 21.71 | +6.09% |

**两条可确认的结论：**

1. **涨跌基准一致** ✅ 东财开盘 35.80 / 收盘 21.71 是 −39%，却写 +6.09% ——
   两个数互斥，证明它必然是拿**收盘跟上周期收盘**比的。
   与我们的 `chg = close ÷ prev_close − 1` 同一个口径。

2. **东财的 `open` 疑似与其它价不同基准** ⚠️ 由其涨跌幅反推前收 = 21.71 ÷ 1.0609 = **20.46**，
   振幅 8.89% 意味着价格区间约 1.82 —— **装不下 35.80 的开盘价**。
   这正是第 4 节描述的「`open` 没跟着其它价一起折算」。
   我们三档的 `open` 都稳稳落在 `[low, high]` 内。

**一条没能验证的**：东财涨跌幅**符号相反**（+6.09% vs 我们 −5.36%）。
可能是前复权锚点不同（东财按当天 10-13 锚定，我们按全库最新 10-12），
也可能截图中那根不是同一周（y 轴刻度看不清）。**此条不下结论。**

### 8. 验证结果（2026-10-13 实测）

覆盖 `SH.600570` 全量：日线 5435 根 × 三复权，派生周期 1542 根 × 三复权。
除权日清单取自 `stock_xdxr`，涨跌恒等式跨「库里存的 chg_amt」与「接口下发的昨收」两个系统。

| # | 判据 | 通过 |
|---|---|---|
| 1 | 日K 昨收 == 库里 `pre_close`（复权档验同倍缩放） | 16305 / 0 |
| 2 | **昨收 + `chg_amt` == 今价**（除权日逐根） | 69 / 0 |
| 3 | 派生周期 `pre_close` 语义（`none` 恒 None / 复权档自洽） | 4176 / 0 |
| 4 | 复权档 相邻两根源子比 == `1 + chg_pct` | 10822 / 0 |
| 5 | 周期桶 `xdxr_date` 标注 | 267 / 0 |
| 6 | **前端回落**：上一根 `close` + `chg_amt` == 今价 | 1388 / 0 |

第 2 条是本次改动唯一要证明的东西 —— **改之前 23 个除权日全部不成立，改之后全部成立**。
第 6 条专门验删列之后前端 `extra?.preClose ?? prevClose` 的回落分支：
`kline_period` 不再下发 `pre_close`，涨跌两列的基准仍是上一根 `close`，两端自洽。

`verify_query_paths.py`（删末根 → 回退聚合 → 还原）四周期口径一致，跑完 `kline_period` 仍 1542 行。

#### 实施中发现并修掉的一个坑

`db.py` 的 `MIGRATIONS` 里有一条 `for col in (pre_close, chg_pct) for table in (day, period)`
的双层循环。`_KLINE_PERIOD_DDL` 删了 `pre_close`，这个循环**没同步** ——
任何进程跑一次 `init_schema()` 就把它加回来（`ADD COLUMN` 落在末位，肉眼看像新列）。
同一文件的注释写着「pre_close 列已删」，代码却在加回来。已拆成两条独立登记。

> 教训：一张表加了列、另一张删了列时，别用双层循环一把梭。

#### 一处数据缺口（非本次改动引入）

`stock_xdxr` 的 `category=1` 有 **24** 条，实际可判定的除权日只有 **23** 个，
差的那天是 **2005-08-09**（10 送 4）：它是日线数据区的**第一条**（该股 2005 年只有 216 行，
8 月只有 08-09 之后的 17 天），没有前一根 `close` 可比，判不出基准跳空。

后果是那一周的复权因子少折一次，浮窗也不会标它。**属数据完整性问题，不在本次范围。**

#### 一处已知的既有偏差

复权档的 `pre_close` 取「桶内首日前收 × 因子」，而 `chg_*` 的基准取 `LAG(close)`（上一根桶收盘）。
含除权的桶里两者因子不同，偏差约 **1.9e-4**（实测 2008-05-30 周桶 84.6575 vs 84.6740）。
恒等式「昨收 + 涨跌 == 今价」仍成立（残差 0.0026%），**改动前后一致**，不在本次范围。
