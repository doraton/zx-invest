## 2. 方案一：本地文件接入（已落地）

### 2.1 原始输出格式

> ⚠️ 以下**全部是本机实测**，不是官方文档——0AMV 没有公开 API。
> 以 `server/src/server/external/znz_0amv.py` 的实现为准。
> 记录日期 2026-10-09，指南针装在 `D:\application\finance\compass`。

> **本项目只要收盘后的日 K，不做分时。**
> 因此主数据源就是 **`day.vdat`** 一个文件——它存着全历史 8219 根日线，
> 且每根的 OHLC 是**收盘后算好的最终值**。
> `.fde` 是盘中缓存，只为「今天还没收盘」服务，**当前不纳入链路**，
> §2.1.2 保留格式说明备查即可。

**接口说明**：

> 无官方接口。本项目自建解析器 `znz_0amv.py`，输入指南针安装目录，
> 输出 `{trade_date: {open, high, low, close}}` 的日线字典。
> 数据源是客户端落盘的二进制缓存而非网络请求，
> 因此**没有 token、没有积分、没有限流、也没有频率窗口**。

**输出参数**（全部来自 `day.vdat` 的 28 字节记录）：

| 名称 | 类型 | 默认显示 | 来源 | 描述 |
|---|---|---|---|---|
| `trade_date` | `datetime.date` | Y | 记录的 `date` 字段（uint32 `YYYYMMDD`） | 交易日 |
| `open` | float | Y | 记录的 `O` 字段 | 开盘价 |
| `high` | float | Y | 记录的 `H` 字段 | 最高 |
| `low` | float | Y | 记录的 `L` 字段 | 最低 |
| `close` | float | Y | 记录的 `C` 字段 | 收盘价 |

⚠️ `trade_date` 是**返回字典的键**、不是字段——`parse_day_vdat()` 返回
`{datetime.date: {open, high, low, close}}`。

`volume` / `amount` **原值返回、不换算**（口径未查明，见 §2.1.3）。
`pre_close` / `chg_pct` / `chg_amt` / `code` 是**入库时**才派生的，
不属于「解析出来的」那部分。

「默认显示」沿用 Tushare 的列义：*不额外指定时是否随结果返回*。
本地解析器**没有 `fields` 参数**，该列恒为上表所列，仅为与 Tushare 文档对齐。

**输入参数**（`parse_day_vdat()` / `fetch_daily()`）：

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `compass_root` | `Path` | 必填 | 指南针安装目录，内部拼出 `ANALYSE\Data\ChinaStk\Z_SK\day.vdat` |
| `since` | `date` / `None` | `None` | 只保留该日期及之后（含）。`None` = 全历史，实测 **8219 条** |

`fetch_daily()` 另有两个 `.fde` 相关参数 `today_only`、以及 `.fde` 分支——
**只关心日 K 时不需要它们**，后续接入脚本走 `parse_day_vdat()` 即可。

#### 2.1.1 `day.vdat` 格式解析

**文件整体**

```
路径  <compass>\ANALYSE\Data\ChinaStk\Z_SK\day.vdat     ⚠️ 是 Z_SK\，不是 ZNZ_\

一个文件混放多个标的的序列。0AMV 的数据页以 28 字节定长头标识：
    b"Z_SK0AMV" + 20 个零字节
```

解析器**严格按这 28 字节比对**来定位页，不做「值看起来合理」的启发式扫描——
同一文件里还有别的标的序列，启发式会误取。页内布局：

```
┌─────────────────────────────────────────────┐
│ 28 字节   数据页头  b"Z_SK0AMV" + 20 个零字节 │
├─────────────────────────────────────────────┤
│ 最多 250 条 × 28 字节                        │
├─────────────────────────────────────────────┤
│ 20 字节   页尾                                │
└─────────────────────────────────────────────┘
```

**单条记录 28 字节（小端）**

`struct.Struct("<fIfffff")`，共 7 个字段，**顺序就是文件里的物理顺序**：

| 偏移 | 类型 | 字段 | 本项目怎么用 |
|---|---|---|---|
| 0 | float32 | `amount` | ✅ **原值入库**（口径未确认，§2.1.3） |
| 4 | uint32 | `date` | ✅ `YYYYMMDD` → `datetime.date` |
| 8 | float32 | `O` | ✅ 开盘价 |
| 12 | float32 | `H` | ✅ 最高 |
| 16 | float32 | `L` | ✅ 最低 |
| 20 | float32 | `C` | ✅ 收盘价 |
| 24 | float32 | `volume` | ✅ **原值入库**（口径未确认，§2.1.3） |

**本机实测的页构成**（2026-10-09，文件 9,541,518 字节）：

```
35 个匹配页
  ├─ 32 个满页   × 250 条
  ├─  1 个页    × 219 条  ← 最后一页，装不满
  └─  2 个空页   ×   0 条  ← 索引占位，首记录过不了校验
                    ─────
              合计  8219 条  = 32×250 + 219
```

⚠️ **35 处命中里只有 33 处是真数据页**。判据是**页距**：页连续排布，间距恒为
`7048 = 28 + 250×28 + 20`，实测 31 个相邻间距全部等于 7048；另有 2 处间距是
412 和 6,100,000，明显不在网格上——它们落在别的结构内部（同文件混有
`Z_SK0B01` / `Z_SK0DMV` 等兄弟序列的 magic），属**误匹配**，解不出有效记录自然被丢弃。

所以**不能用「页数 × 250」估算记录数**，也不能靠文件大小判断数据完整——
必须逐条解、逐条校验。这个 7048 固定页距也可作为将来的完整性校验位。

**有效性校验**（`_valid_ohlc`）：

```python
o > 0 and h >= l > 0 and h >= max(o, c) and l <= min(o, c)
```

刻意**不设「值必须大于某阈值」的下限**——0AMV 在 1993 年只有 3.1，
用 `OHLC > 1000` 这类阈值会把早期真实历史全毁掉。

**⚠️ 锁**：`day.vdat` 在指南针运行中会被独占锁定读不了，
这是接入时最容易踩的坑，详见 **§2.5**。

#### 2.1.2 `.fde` 格式（当前不使用，备查）

盘中缓存，**只为「今天还没收盘」准备**。既然本项目只做收盘后的日 K，
它当前不在链路里——但格式仍记录在此。

```
路径  <compass>\Temp\Z_SK0AMV__.fde
      （另有 Z_SK0AMV<日期>.fde 历史快照，15 个里 10 个有效、5 个是 20 字节空壳）

24 字节头
    0    4 字节    magic b"2ACR"     ⚠️ 本机是 .fde/2ACR，上游仓库描述的 .cde/XADR 不适用
    4    uint32    日期 YYYYMMDD
    8    uint32    **单条记录长度 = 16**
    12   uint32    **固定常量 145900**（14:59:00）
    16   uint32    声明 body 长度 = 3824
    20   uint32    **固定常量 93059**（09:30:59）
body：16 字节/条，实际条数取 (文件长度-24)//16
    struct.Struct("<fffI")   value, volume, amount, time(HHMMSS)
```

单条记录解出来的样子（2026-10-09 的文件，共 238 条，摘首末）：

```python
{'value': 150852.296875, 'volume': 3704055296.0, 'amount': 56710344704.0, 'time': 93159}
{'value': 153790.109375, 'volume': 115518627840.0, 'amount': 1883322843136.0, 'time': 145859}
```

它只有瞬时 `value`，OHLC 得**现推**（首值 / 末值 / max / min）；
且 `close` 截止最后一次采样（实测 14:58:59），收盘前还会变。

- **头部常量**：偏移 8 / 12 / 16 / 20 在 2025-09-15、2025-10-10、2025-10-13、
  2025-11-25 等**不同日期**文件里取值完全相同（16 / 145900 / 3824 / 93059），
  所以 12 与 20 是采样窗口的固定端点常量，不是当日实际起止时刻。
  偏移 16 声明的 3824 与实际 body 长度 3820 差 4 字节，条数必须按**实际长度**算。
- **采样间隔**：238 条里 236 次恰好 60 秒，唯一例外是午休
  `11:29:59 → 13:00:59`（跳 5460 秒）。首条 09:31:59、末条 14:58:59。
- **`time`** 是打包的 `HHMMSS` 十进制数，`93159` = 09:31:59。

#### 2.1.3 量额口径（`day.vdat` 采集，`.fde` 丢弃）

**`day.vdat` 的 `volume` / `amount` 原值入库**（2026-10-09 起由「忽略」改为采集）。
理由是：口径虽未查明，但它们**内部自洽**、且是文件里确实存在的证据，
存下来成本为零，将来查明单位后再决定换算或改列名即可。

2026-10-13 实测 8220 条全量：

| | `day.vdat` **（入库）** | `.fde`（不取） |
|---|---|---|
| 有值吗 | ✅ 8187/8220 条有值，仅 33 条为 0（对应 33 个数据页的**每页首条**） | ✅ 每条都有 |
| 两字段自洽吗 | ⚠️ `amount ÷ volume` **集中在 8~22**（均值 11.3、77.7% 落在带内），但全区间跨 **0.12~102.54**、**随年代收窄**（1990s 离散度最大）——所以「稳定在 8~22、30 年没变」这个说法不成立 | ❌ 末条 `amount ÷ value` ≈ **1.2e7** |
| 与 0AMV 价格的关系 | ❌ **不是价格**：`amount ÷ volume ÷ close` 从 1993 年的 ~0.99 漂到 2026 年的 ~1e-4 | ❌ 不自洽 |
| 落库列 | `kline_0amv.volume` / `.amount`，**原值不换算** | 不入库 |

⚠️ **这两列不是「成交量·手 / 成交额·千元」**，与 `kline_day` 的同名列语义不同，
所以 `kline_0amv` 的列注释不写「手 / 千元」，只写「原始值，口径未确认」。
⚠️ `.fde` 的量额连内部都不自洽，且与 `day.vdat` 不同口径，故 `.fde` 路径返回 `None`，不并入日线。

### 2.3 数据流

```
指南针客户端
  └─ ANALYSE\Data\ChinaStk\Z_SK\day.vdat    全历史日线 8219 根（唯一数据源）
              │
              ▼    每天收盘后跑一次

              │
              ▼    按 since=上次同步日 过滤，只剩新增的那根

```

`.fde` 不在这条链路上（§0 已说明为何搁置），格式备查见 §2.1.2。

### 2.4 两个文件各自能解析出什么

| | `day.vdat` **（在用）** | `.fde`（搁置） |
|---|---|---|
| 路径 | `ANALYSE\Data\ChinaStk\Z_SK\day.vdat` | `Temp\Z_SK0AMV__.fde` |
| 单条大小 | 28 字节 `<fIfffff` | 16 字节 `<fffI` |
| **能解出什么** | `date` `open` `high` `low` `close` `volume` `amount` | `value`（+两个量额，不自洽不取）、`time` |
| 解出什么结果 | 一天一根日线 OHLC + 原始量额 | 一行 OHLC + `samples` 采样点数 |
| **覆盖范围** | **19930103 ~ 20261008，8219 根**，全历史 | 只有**当天**，238 个采样点 |
| 内容性质 | 收盘后的最终值，当天已定 | 盘中实时值，最后一条是 14:58:59 |
| 何时用 | 全量冷启动、每日收盘后补当日 | 收盘前拿当日最新值——**当前不需要** |
| 会被锁吗 | ⚠️ 客户端运行时锁住读不了 | 不会 |

**为什么只用 `day.vdat` 就够**：它一个文件就覆盖了**全部历史 + 每天的收盘值**，
收盘后跑一次即可拿到当天最终值——**不需要实时性**。
`.fde` 唯一不可替代的场景是「今天还没收盘就想看盘中值」，
而本项目不关心盘中，所以整个 `.fde` / OCR 路线一并搁置。

### 2.5 ⚠️ 锁是最大的坑

指南针**运行中**打开 0AMV 页面时，`day.vdat` 被独占锁定，Python 读会抛
`PermissionError`（`Copy-Item`、`FileShare.ReadWrite` 同样被拒）。

**抛的是权限错误，不是解析错误，绝不能误判成「文件里没有数据」。**
2026-10-09 实测踩过：锁着时只解出 276 条稀疏记录，关掉客户端后同一文件是完整的 8219 条。

→ **对策**：每日调度安排在收盘后、且**避开用户开着指南针的时段**；
全量补历史必须先完全退出客户端。`read_file()` 已把这个转换成可操作的报错文案。

| 项 | 值 |
|---|---|
| 表 | `kline_0amv`（`code = '0AMV'`），**独立 10 列结构**（无 `pre_close` / 无 `ah_*`） |
| 行数 | **8220**（2026-10-13 实测） |
| 区间 | 1993-01-03 ~ **2026-10-09** |

| `chg_amt` / `chg_pct` | 由前一根 close 派生；首行 1993-01-03 为 `NULL`（无前一根） |
| 校验 | 行数/日期集合/OHLC/量额/涨跌额逐行比对，**全部一致**；OHLC 关系违例 0 |

> ⚠️ **本文其余章节出现的「8219 条 / 末根 20261008」都是 2026-10-09 当时的源文件快照。**
> 源文件 `day.vdat` 此后仍在增长，**当前实际条数尚未复核**——2026-10-13 尝试重测时
> 指南针客户端正在运行、文件被独占锁定（见 §2.5 的 `PermissionError` 陷阱），
> 须**完全退出客户端**后才能重新数一遍并同步更新 §1、§2.1、§2.3、§2.4 里的数字。
> 在此之前，以本表这组**落库后**的数字为准。

入库命令：

```bash
cd server
.\.venv\Scripts\python.exe tools\sync_znz.py                  # 全量
.\.venv\Scripts\python.exe tools\sync_znz.py --dry-run       # 只解析不写库
.\.venv\Scripts\python.exe tools\sync_znz.py --start 2026-01-01   # 增量
```

脚本用 `ON DUPLICATE KEY UPDATE`，**可重复执行**，不会产生重复行。

> ⚠️ 值精度：`day.vdat` 是 float32，库里存 `DECIMAL(12,2)`（2026-10-09 从 4 位收窄）。
> 收窄的依据是 float32 自身的分辨力：在 0AMV 常用的 ~152000 量级上，
> float32 的 ulp = `2^17 × 2^-23` = **0.0156**——源数据本来就只能分辨到 0.0156，
> 存 4 位那 3、4 位小数是浮点残渣。行情软件显示涨跌幅也只到 2 位。
> 早期数值小（如 `high=16.80000114`）入库后是 `16.80`，绝对误差约 1e-3，
> 属存储精度而非数据错误。

## 4. 方案二：分时盘中值（已搁置）

**因为本项目只做收盘后的日 K，方案二整体搁置**，包括 `.fde` 路线。
`day.vdat` 收盘后跑一次就能拿到当天最终值，**没有实时性需求**。

保留这一节是为了记录**如果将来确实要做盘中值**时的备选方案，
以及当初评估过什么——不是待办。

触发这个议题的条件（满足任一才值得重启）：

- 要做盘中提醒 / 盘中盯盘
- 要在收盘前拿到当日值（而不愿等到收盘后）
- `day.vdat` 长期读不到（权限 / 锁 / 文件格式变更）

`.fde` 其实已经能提供当日最新值，真要重启时**先用它**（零成本），
不够再考虑下面两条：

| | OCR 像素解析 | 图像识别大模型 |
|---|---|---|
| 原理 | PaddleOCR 读坐标轴数字 + OpenCV 找 K 线柱体 | 把截图喂给多模态模型，直接问出 OHLC |
| 精度 | 坐标插值 + 像素测量，**可量化误差** | 语义理解，误差不可直接量化 |
| 成本 | 一次性开发，无 token 费 | 每次调用付费 |
| 依赖 | 本机装 PaddleOCR | 需要 API key / 本地部署 |
| 脆性 | 客户端改配色就废 | 相对鲁棒（能读懂就答） |
| 适合 | 高频每日、追求零边际成本 | 低频、追求开发速度 |

### 4.1 OCR 路线（保留原设计）

数据流：

```
指南针客户端(登录 + 联网 + 前台，0AMV 图表显示在主图区)
   │ 截图主图 Pane
   ▼
PaddleOCR → Y 轴价格 + X 轴日期
OpenCV    → 红绿 K 线柱体轮廓
   │ 坐标插值
   ▼
(date, open, high, low, close) × N
   │
   ▼
upsert kline_0amv
```

**关键实现点**（都是实测踩出来的）：

- **Y 轴插值**：OCR 拿到 ≥2 个「Y 轴像素 → 价格」锚点后线性插值。
- **X 轴插值**：同理，用底部日期标签定每根 bar 的横坐标。
- **`FIRST_VALUE` 陷阱不适用**（那是物化侧）；OCR 侧对应的是
  `open` 必须取**柱体实体的首个像素价**而不是最左边的像素——
  一根 bar 的实体有宽度，取错一根就差一根的开盘价。
- **OHLC 关系必须校验**：`h >= max(o, c)`、`l <= min(o, c)`、`o > 0`。
  不设「值 > 某阈值」的下限——0AMV 早期只有几千亿，阈值会毁掉老历史。

**截图的三个前提**：

1. 窗口必须已恢复（防最小化）
2. 窗口必须在**前台**（后台截图会拿到空白/遮挡）
3. K 线图必须显示 0AMV

### 4.2 图像识别大模型路线（新增候选）

把主图截图直接交给多模态模型，配一个严格的输出契约：

```
提示词要点：
  - 只回 JSON，不要解释
  - 字段：date, open, high, low, close
  - 看不清就填 null，不要猜
  - 日期用 YYYYMMDD
```

再叠一层校验：拿模型给的 OHLC 跑 §4.1 那套关系校验，
不满足就丢弃并告警。**这一步不能省**——模型会自信地给出看起来合理但错位的数字。

成本上，每天 1 次调用 × 约 2000 输入 token，比 OCR 的开发成本低得多；
如果只是每天补一根收盘值，这个方案性价比更高。

### 4.3 建议

**维持搁置。** 先把方案一（`day.vdat` + 每日收盘后调度）跑通，
它零成本、零依赖、覆盖面最全。方案二**不要在没被需求逼到之前做**——
尤其别先投入 OCR / VLM 开发。

真到了要做盘中值的那天，顺序是：
先 `.fde`（已实现、零成本）→ 仍不够才 OCR → 最后才 VLM。

## 5. 表结构

`kline_0amv` 有**独立的 DDL**（`_KLINE_0AMV_DDL`，见 `server/src/server/db.py`），
**不**复用 `kline_day` 的 `_KLINE_DDL`。与 `kline_day` 的差异都是业务性质决定的：

| 列 | 说明 |
|---|---|
| `code` | 固定 `0AMV`（首字符是数字 0） |
| `trade_date` | 交易日，主键 |
| `open` `high` `low` `close` | 0AMV 日线 OHLC，不复权 |
| `chg_amt` | 涨跌额 = close − 前一交易日 close |
| `chg_pct` | 涨跌幅 % = (close − 前一交易日 close) / 前一交易日 close |
| `volume` `amount` | **day.vdat 原始值，不换算**；口径未确认，**不是**「手 / 千元」 |

**为什么没有 `pre_close`**：0AMV 是「活跃筹码流通市值加总」，股本变动时价格反向等比、
市值恒定，不存在需要修正的除权断层——前收就是前一交易日 close，单独存一列是冗余。
**为什么没有 `ah_vol` / `ah_amt`**：没有「盘后固定交易」这回事。

主键 `(code, trade_date)`，无二级索引（理由同 `kline_day`）。

⚠️ `kline_0amv` 不参与 `kline_period` 的物化——它没有周/月/季/年派生，
`sync_state` 里也没有它的行。
