# K 线根数档位对照

> ← 返回 [架构说明](architecture.md)

主图向前翻历史时，一次加载多少根、能回溯到哪一年 —— 这张表是选参数时的参照。

## 常用档位

数据基准：`zx_invest.kline_day` 里的 **`SH.600570`（恒生电子）**，共 **5435** 根，末日 **2026-10-12**。
（库名 `zx_invest` 是 2026-10-09 由 `tsdb` 改名而来；`code` 唯一形态是**大写带点**。）

| 根数 | 起始日期 | 跨度 |
|---|---|---|
| 200 | 2025-12-10 | 0.8 年 |
| 300 | 2025-07-15 | 1.2 年 |
| 500 | 2024-09-11 | 2.1 年 |
| 1000 | 2022-08-22 | 4.1 年 |
| 2000 | 2018-07-11 | 8.3 年 |
| 3000 | 2014-05-07 | 12.4 年 |
| 5000 | 2005-11-14 | 20.9 年 |
| 5435 | 2003-12-16 | 22.8 年（全量） |

> ⚠️ 这张表是**快照**，每同步一次就会漂。取实时值：
> `SELECT trade_date FROM zx_invest.kline_day WHERE code='SH.600570' ORDER BY trade_date DESC LIMIT 1 OFFSET <n-1>`
> ——注意用 `SH.600570`，用小写 `sh600570` 返回 0 行、不报错。

**跨度算法**：`(末日 - 起始日) / 365.25`，按自然年算。折合 A 股约 238 个交易日/年，
所以 500 根 ≈ 2.1 年、1000 根 ≈ 4.1 年。

这张表只对**恒生电子**精确成立。不同股票的上市日期不同，全量根数会不一样：
1990 年代上市的能到 6000~7000 根，2015 年后上市的只有一两千根。选参数时用「跨度」那列对齐，
不要直接套用「根数」。

## 当前配置

`web/src/config/api.ts`：

| 常量 | 值 | 含义 |
|---|---|---|
| `INITIAL_BARS` | 500 | 首屏加载根数（2.1 年） |
| `PAGE_BARS` | 500 | 每次拖到左边界追加根数 |
| `MAX_COUNT` | 1000 | 单次请求后端硬上限（`market.py` 的 `MAX_COUNT`） |

两者同值 500，所以加载档位是 `500 → 1000 → 1500 → …`，正好对上表里的每一档。

**不设总量上限。** 一直翻到后端返回 `truncated=false`（即库里最早的那根）为止，
提示条显示「已加载 N 根，已到最早的历史数据」。

## 为什么不需要上限

之前设过 `MAX_LOADED_BARS = 1000`，理由写的是「内存上限」。实测下来这个理由不成立：

| 根数 | 堆内存 | gzip 传输 |
|---|---|---|
| 500 | 81 KB | ~12 KB |
| 1000 | 162 KB | ~25 KB |
| 3000 | 485 KB | ~75 KB |
| 5432（全量） | **878 KB** | ~140 KB |

堆内存按转成 klinecharts `KLineData`（`timestamp` + OHLC + volume，6 个 double 字段）
实测约 **166 B/根**。全历史 5432 根不到 1 MB，浏览器完全扛得住。

真正随根数放大的**不是内存而是 CPU**：每次前插数据，klinecharts 都要对整个 `_dataList`
重算全部指标（MA/MA10/MA20 + VOL + MACD + KDJ + BOLL 共 7 条序列）再重绘 canvas。
5432 根仍是毫秒级，但这才是放开上限时要关注的指标。

内存要到**全市场**规模才会紧张：1728 只 × 约 5000 根 × 166 B ≈ 1.4 GB。
单页一次只看一只标的，用不到那个量级。

## 加载机制

每次拖到可视区左边界（klinecharts 内部判据 `from === 0 && _dataLoadMore.forward`）
就发**一个**请求，加载一页，不会连发：

```
GET /api/index/kline?code=<code>&category=<n>&adjust=<a>&count=501&end_date=<已加载最早日期>
```

- `count` 是 `PAGE_BARS + 1`。闭区间查询（`end_date` 含当天）必然把游标当天带回来一根，
  前端按 `datetime < cursor` 剔掉，净增正好 500 根。
- 前插后视区不动，所以 `from` 会从 0 变成 500，不会立刻再触发一轮。
- `end_date` 一路向左推，闭区间导致相邻两页重叠 1 根 —— 这是刻意的：
  重复可以在前端去重，空隙是数据丢失。

相关代码：`web/src/pages/MarketChart.tsx` 的 `setDataLoader({ getBars })`。

## 复现这张表

```sql
-- 库名是 zx_invest（原名 tsdb，2026-10-09 改名）；code 是大写带点的 SH.600570
SELECT trade_date FROM zx_invest.kline_day
WHERE code = 'SH.600570' ORDER BY trade_date DESC;
```

取倒数第 N 个即「N 根」的起始日。

⚠️ 早先这里写「注意要连 `tsdb`，不是 `mysqldb` / `tq-stock`，用错库算出来的档位会整体偏」——
那三个库**现在一个都不存在**了（本机只有 `zx_invest` 一个业务库），
`tsdb` 是 2026-10-09 的旧名。照着敲会直接报 `Unknown database`。
