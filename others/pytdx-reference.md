## 0. 一句话定位

pytdx 是**唯一能给到 2010 年前历史 + 真实成交额**的 A 股网络源，
但**上游已归档、个人维护**，协议再变一次就没有人会修。
它有一条由社区补丁、自我改造、三源互校三层兜住的数据管道。

## 2. 优点

### 2.1 唯一能给到 2010 年前历史

本机实测：腾讯 HTTP 拉到 2010-01-04（恒生电子 4000 根），
本地通达信 `.day` 文件 99% 只到 2020-01-02，
pytdx 是**唯一**能补 2010–2019 这段历史的网络源。

### 2.2 唯一能拿真实成交额的网络源

腾讯 K 线没有 `amount` 字段（每行只有 6 个值），
pytdx 日线协议的 `amount` 字段精确到元（4 字节 IEEE 754 浮点，
`amount >= 16,777,216` 后开始丢精度——大盘股全市场成交额会受影响，
但 A 股日线成交额 ≤ 16.7M 的标的精度无问题）。

### 2.3 能给财务快照与除权除息

| 接口 | 能力 |
|------|------|
| `get_finance_info` | 37 字段，**仅最新一期**（无日期参数） |
| `get_xdxr_info` | sh600570 全历史 46 条 |

腾讯 / 东方财富的公开接口**都不提供这两类数据**。

### 2.4 已知 8 台可用服务器

内置 104 个 `hq_hosts`，全量扫描后只有 8 台能真正返回 K 线
（`117.34.114.13/14/15/16/17/18/20/27:7709`，国泰君安），
固化在 `config.TDX_HOSTS`。

**指数与个股的可用性完全相同**，不存在「只服务指数」的限制。
8 台数据交叉比对完全一致，2026-10-05 复测延迟 176–228ms。

### 2.5 全周期能力（含分钟线）

| 周期 | category | 表现 |
|------|---------|------|
| 日K | 4 | ✅ 完全可用 |
| 周K / 月K | 5 / 6 | ✅ OHLC 和 amount 正确 |
| 季K / 年K | 10 / 11 | ✅ OHLC 和 amount 正确 |
| 5/15/30/60/1 分 | 0/1/2/3/8 | ✅ 全部正常解析 |

腾讯 HTTP 只给日/周/月三个周期（不带分钟线）；
pytdx 是少数能给到 5/15/30/60/1 分钟的网络源。

### 2.6 分页参数上限 800 根 / call

`get_security_bars(count=800)`，单次最多 800 根，
拉 4000 根 5 次往返即满。

### 2.7 经过三源互校

`architecture.md §3.4` 的对照实验里，
pytdx × 腾讯 × 东财互校 **18018 根日线**：

- 开盘价 **0 处差异**（18018 根逐位相同）
- 交易日历 **18018/18018 对齐**
- 用 18018 根的强一致性**反推出了腾讯 2011-12 的数据缺陷**

## 3. 缺点 / 已知局限

### 3.1 上游已归档，不可修复

最后 push 是 2020-04-15，GitHub 标记 `archived`。
任何 bug 修复、协议适配、新节点添加都得**自己长期维护**。
这一条与「它今天能不能跑」无关，但决定了「能不能长期依赖它」。

### 3.2 没有复权接口

**完全不支持 qfq / hfq**。
`get_security_bars` 只返回不复权价。要复权得：
- 自己算（参考 tdx2db AGENTS.md 的涨跌幅复权 factor 法）
- 或者去拉腾讯/东财的 `fqt` 参数
- 或者读 `stock_xdxr` 自行处理

### 3.3 只能连接到 8 个免费节点

| 结果 | 数量 |
|------|------|
| 能返回 K 线 | **8**（`117.34.114.13/14/15/16/17/18/20/27:7709`） |
| 连接成功但任何接口都无数据 | 25 |
| 连不上 | 71 |

8 台是国泰君安的免费节点，**无 SLA、无并发上限文档、
无收盘高峰表现数据**。一旦这 8 台都挂了，pytdx 就废了。

### 3.4 几个关键接口都返回 None / 空

| 接口 | 表现 |
|------|------|
| `get_security_list` | 8/8 节点返回 **None** |
| `get_block_info` | 返回**空** |
| `get_transaction_data`（逐笔） | **None** |
| 副图指标（MACD / KDJ / BOLL） | **无任何接口** |

意思是：
- 不能枚举「现在有哪些股票在交易」（要靠代码表或本地 .tnf）
- 行业/省份名翻译不出来
- 逐笔拿不到，筹码分布只能近似
- 副图指标全部在前端现算

### 3.5 非日线 vol 的单位是「手」

| 周期 | vol 倍率 | amount |
|------|----------|--------|
| 日K | **1.0000** | 1.0000 |
| 周/月/季/年K | **0.0100** | 1.0000 |

也就是说日线 vol 是「股」，其他周期是「手」——同一列混用两种单位，
代码里必须处处记得 ×100，否则 1.3% / 2% 这种回测误差不知不觉就来了。

### 3.6 K 线报文有隐蔽陷阱：尾部 extra 字段长度不固定

K 线报文尾部有一个**长度因标的而异**的保留字段：

```
date(4)  open/close/high/low(varint，相对基址差值)  vol(4)  amount(4)  extra(N)
```

| 标的 | 正确的 extra |
|------|-------------|
| **个股** | **0 字节** |
| **指数** | **4 字节** |

- pytdx 原版写死 0 → **只对个股正确，指数逐根错位**
- 网上流传的「补 4 字节」补丁 → **只对指数正确，个股越界读出垃圾日期**

两个方向都很隐蔽：价格靠基址递推，看着一直正常，
**只有日期会露馅**。

### 3.7 异常会被静默吞掉

`get_security_bars` 被 `@update_last_ack_time` 装饰，
`TdxHq_API(raise_exception=False)` 时**捕获所有异常返回 `None`**，
导致「解析崩溃」与「服务端没数据」完全无法区分。

这是 `sweep_stock_bars.py` 一度误判「免费节点不提供个股 K 线」的
直接原因。

### 3.8 单次最多 800 根 / call，且 `count` 过小会返回稀疏数据

拉 4000 根要翻 5 页。
拉 `category` 10/11 时 **count 必须给足**（本项目用 400），
count 过小（如 60）时服务器返回稀疏数据、间隔被拉长，
看着像日期乱序，曾被误判为「数据损坏」。

## 4. 实测中的关键发现

下面每条都是**我们自己先下错结论、后来用数据纠正的**——属于经验沉淀，
不绑定具体项目架构。

| # | 一度得出的结论 | 事实 | 根因 |
|---|----------------|------|------|
| 1 | 「免费节点不提供个股 K 线，一个都没有」 | 8 台全部个股通 | `raise_exception=False` 吞异常 + extra 补丁对个股错 |
| 2 | 「周/月/季/年线不能用」 | OHLC 和 amount 正确，只有 vol 单位是「手」 | 把「单位差异」误判成「数据损坏」 |
| 3 | 「腾讯 2011-12 数据不对，说明 pytdx 错了」 | 是我误读了 `verify_stock.py` 的**周线**输出当作日线 | 验证脚本输出的周期没读清 |
| 4 | 「通达信公开服务器已失效」（引自社区报告） | 5 个市场全部正常，只有逐笔不通 | 未实测就采信二手结论 |

## 5. 我们对它的改造（属于工程经验，非项目专属）

代码位置：`server/src/server/external/tdx_kline.py`

### 5.1 `raise_exception=True` —— 硬约束

所有连接都用 `TdxHq_API(raise_exception=True)`，
失败带原始异常暴露出来。否则就是 §3.7。

### 5.2 extra 长度自动探测 —— 不写死任何值

按候选值 `(0,4,8,12,16,20)` 逐个试探，取第一个满足三条件的布局：

1. 能走完 `ret_count` 根
2. **正好消费完整个 `body_buf`**
3. 结果合法：年份 1990–2100、`high >= low > 0`、**完整时间元组 `(y,m,d,h,minute)` 严格单调**

第 3 条用完整时间元组而非仅日期，是为了接受分钟线一天多根的情况；
用「严格单调」而非「升序」，是为了同时接受升序和降序布局。

### 5.3 其他修正

| 修正 | 内容 |
|------|------|
| `fetch_xdxr` 字段映射 | `transfer_ratio` 曾误用 `peigujia` → 改为 `reduce_ratio=suogu` 等 |
| `stock_xdxr.category` | 主键列必须 `NOT NULL DEFAULT 0`，否则 MySQL 1171 错误 |
| `tdx_local.read_day` | 日期格式化 bug：`f"{d:04d}"` → `d // 10000` |

## 6. 验收证据（实测，不绑定项目）

| 验收项 | 结果 |
|--------|------|
| 恒生电子日线 vs 本地 `.day` | 库内 4000 根，其中 1636 根与本地可比，**逐根全一致** |
| 四周期物化 vs Python 重算 | week/month/quarter/year **全部一致** |
| OHLC 关系违例 | **0 条**（4000 根，2010-01-04 ~ 2026-09-30） |
| 查询双路径口径 | 一致 |
| **三源互校** | pytdx × 腾讯 × 东财，**18018 根**日线：<br>开 **0 处差异**，交易日历 **18018/18018 对齐** |

三源互校这一项尤其重要：它不仅验证了 pytdx，
还**用它发现了腾讯 2011-12 的数据缺陷**——4 只无关个股
在同批日期上同步出现 10%–80% 量差，东财仲裁判定腾讯错。
详见 [architecture.md §3.4](../docs/architecture.md)。

## 8. 风险与应急预案（不含项目特定步骤）

| 风险 | 触发信号 | 通用应对 |
|------|---------|---------|
| 协议变更导致解析错位 | 8 台同时返回异常 / 数据验证脚本失败 | **先停写入**；探测逻辑应给出明确失败而非静默错值 |
| 8 台全部不可用 | 连接超时 | 切其他源（HTTP 源或本地 `.day`） |
| 单台数据异常 | 三源互校发现分歧 | 剔除该台；保留多节点冗余结构 |
| pytdx 彻底停止维护 | 上游 archived + 协议变更 | 迁移 mootdx，或改走纯 HTTP 源 |

**最重要的一条**：因为上游已归档，**不要假设它坏了会有人修**。
所有对它的假设都应该由**自己的验收脚本兜住**，
而不是由「上游还在」这个前提兜住。
